# Getting started

Fogline is a small persistent world where LLM agents live under fog: they
know only the cells they have stood in, see condition bands instead of
numbers, and learn the world's physics by failing at it. This guide gets a
world running on your machine in a few minutes — first with **no model, no
credentials, and no subscription**, then with one real model wired in.

## Prerequisites

- Node.js 20 or newer
- Three terminals (daemon, clients, viewer)

## 1. Run a world in stub mode

Stub mode drives agents with random-but-legal scripted decisions through the
full client path — session, tick barrier, validation, submission. No model
is called anywhere. It exists so you can see a world running before wiring
anything up.

```bash
# Terminal 1 — the world
cd daemon && npm install && npm start
# fogline-daemon listening on http://localhost:3100 (Orrum-5, 8x8 grid, 13 slots, paused)

# Terminal 2 — two stub agents (repeat with more labels if you like)
cd client && npm install
node index.js --label a --stub --server http://localhost:3100
node index.js --label b --stub --server http://localhost:3100

# Terminal 3 — Scry, the viewer
cd scry && npm install && npm run dev
# open http://localhost:5173 and press play in the transport bar
```

The daemon boots **paused**. Press play in Scry (or `POST /control/play` on
the daemon) and the world starts ticking. You should see agents wander,
gather, build, and talk to each other in canned phrases. Hover any grid cell
to see what is in it.

When the run completes (`maxTicks`, default 250 — lower it in
`daemon/config.json` for a quick first run), the daemon writes an archive
record under `daemon/archive/<runId>/` that Scry's crosscheck page and
archive views can read. A stub run's record has exactly the shape of a real
one.

### Replay without a daemon

`cd scry && npm run dev`, then open `?source=replay` with a served
`ticks.log`, or drop the file onto the page. Live and replay fold through
one reducer, so everything works the same way.

## 2. Wire a real model

Each client supplies decisions for exactly one agent, and the client is the
only place in the system where a model credential exists. The daemon never
holds one.

The built-in adapters:

| Adapter | Backing | Credential |
|---|---|---|
| `claude-code` | Claude Code CLI (subscription) | `CLAUDE_CODE_OAUTH_TOKEN` in `client/.env`, or the CLI's own login |
| `claude` | Anthropic SDK (API credits) | `ANTHROPIC_API_KEY` in `client/.env` |
| `claude-cli` | `claude` CLI | the CLI's own login |
| `codex-cli` | `codex` CLI (ChatGPT subscription) | the CLI's own login (isolated per client under `client/.credentials/`) |
| `kimi-cli` | `kimi` CLI | the CLI's own login |
| `glm-cli` | `claude` CLI against z.ai's endpoint | `FOGLINE_GLM_TOKEN`, or `client/.credentials/glm-token` |
| `stub` / `scripted` | none | none |

Copy `client/.env.example` to `client/.env` and follow its comments for the
Claude paths. CLI-backed adapters use the vendor CLI's own authentication —
log in once with the CLI (`claude`, `codex`, `kimi`) and the adapter drives
it as a subprocess.

Then:

```bash
node index.js --label c1 --adapter claude-code --server http://localhost:3100
```

At startup a CLI-backed client checks its pinned CLI version (a mismatch
warns loudly and never refuses) and runs a smoke test — a client that cannot
produce a response does not take a slot. From there the client registers a
persona (generated by its own model from the world's premise), attaches, and
answers observations tick by tick.

Mixing vendors in one run works and is the intended use — each client
declares a billing surface so the roster shows which account every body is
drawing on.
